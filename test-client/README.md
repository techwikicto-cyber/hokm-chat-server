# تستر مستقل چت سرور هکم

ابزاری برای بررسی این‌که چت سرور درست کار می‌کند یا نه.

**به سرور چت دست نمی‌زند.** یک صفحه لوکال بالا می‌آورد، شما IP و پورت سرور چت را
وارد می‌کنید، و دو کلاینت سوکت مستقل به آن وصل می‌شوند. هیچ تغییری در کد سرور،
هیچ ری‌استارتی و هیچ متغیر محیطی جدیدی لازم نیست.

## اجرا

```bash
node test-client/server.js
```

سپس در مرورگر: **http://localhost:8080**

پورت را با `PORT` عوض کنید: `PORT=9000 node test-client/server.js`

هیچ پکیجی نصب نمی‌خواهد — فقط Node.

## استفاده

در بالای صفحه سه فیلد را پر کنید و **اتصال** را بزنید:

| فیلد | مقدار |
|---|---|
| آدرس سرور چت | `http://<ip>:<port>` — مثلاً `http://1.2.3.4:3008` |
| کلید AES | مقدار `AES_ENCRYPTION_SECRET_KEY` سرور، دقیقاً ۳۲ کاراکتر |
| نام اتاق عمومی | مقدار `PUBLIC_ROOM_NAME` سرور (پیش‌فرض `public_chat_room`) |

مقادیر در مرورگر ذخیره می‌شوند و دفعه بعد پر هستند.

بعد از اتصال، دکمه **«اجرای همه تست‌ها»** ۹ سناریو را پشت سر هم اجرا می‌کند و
نتیجه هرکدام را با علت شکست نشان می‌دهد. برای تست دستی هم دو پنل A و B هستند
که می‌توانید مستقیماً `get_user_details` / `join_chat_room` / `send_chat_message`
بفرستید و لاگ رمزگشایی‌شده هر دو طرف را ببینید.

## چه چیزی تست می‌شود

| # | تست | چه چیزی را ثابت می‌کند |
|---|-----|------------------------|
| ۱ | اتصال + `get_user_details` | هندشیک سوکت، درستی کلید AES، بارگذاری تاریخچه عمومی |
| ۲ | چت عمومی A → B | پخش پیام در اتاق عمومی و ساختار `sender_details` |
| ۳ | تاریخچه عمومی | `INSERT` و `SELECT` جدول `public_chat` |
| ۴ | اتاق خصوصی | `join_chat_room` و پخش پیام در اتاق خصوصی |
| ۵ | تاریخچه خصوصی | `INSERT`/`SELECT` جدول `private_chat` |
| ۶ | ضدفلود | کول‌داون ۸ ثانیه‌ای روی Redis |
| ۷ | فیلترها | حذف شماره موبایل و کاراکترهای خاص از متن پیام |
| ۸ | ارسال بدون احراز هویت | سرور باید `request_user_details` برگرداند |
| ۹ | ورودی خراب | payload رمزنشده نباید سرور را بیندازد |

## اگر تستی قرمز شد

- **تست ۱ تایم‌اوت شد** → کلید AES یا نام اتاق عمومی اشتباه است.
- **کتابخانه socket.io لود نشد** → آدرس/پورت غلط است یا سرور بالا نیست.
- **تست ۲ تایم‌اوت شد** → معمولاً یکی از این دو:
  - **Redis روی سرور بالا نیست.** سرور قبل از هر ارسال برای کنترل ضدفلود به Redis
    می‌زند و خطایش را فقط `console.error` می‌کند، یعنی پیام بی‌صدا گم می‌شود.
  - سرور در حالت **cluster** پی‌ام‌۲ اجرا شده ولی `SHOULD_USE_NGINX_REDIS=true`
    نیست، پس دو کلاینت روی دو worker مختلف افتاده‌اند و پیام هم را نمی‌بینند.
- **تست ۳ یا ۵ قرمز شد** → مشکل از MySQL است: جدول‌ها، نام ستون‌ها، یا دسترسی کاربر.
- **تست ۶ قرمز شد** → Redis کول‌داون را ثبت نمی‌کند و ضدفلود عملاً غیرفعال است.

## نکات

- سرور پیام را با `socket.to(room)` پخش می‌کند، پس **فرستنده پیام خودش را دریافت
  نمی‌کند**. برای همین دو کلاینت لازم است — همیشه به پنل مقابل نگاه کنید.
- کول‌داون ضدفلود بر اساس `user_id` است. تست‌های خودکار قبل از هر ارسال یک
  `user_id` تصادفی برای کلاینت A می‌سازند تا گیر نکنند. در تست دستی اگر پیام دوم
  رد شد، ۸ ثانیه صبر کنید یا `user_id` را عوض کنید.
- نام اتاق خصوصی اگر عددی و کوچک‌تر از `10000000` باشد، سرور عمداً آن را در
  دیتابیس ذخیره نمی‌کند (ولی پخش زنده انجام می‌شود).
- رمزنگاری AES در پروسه Node این ابزار انجام می‌شود، نه در مرورگر. دلیلش این است
  که Web Crypto فقط روی HTTPS یا localhost کار می‌کند؛ این‌طوری اگر تستر را روی
  خود سرور اجرا کنید و با `http://<ip>:8080` بازش کنید هم کار می‌کند.
- اگر سرور چت با `IS_LOCAL=true` بالا آمده باشد، CORS خاموش است و فقط نمایش
  «health» بالای صفحه کار نمی‌کند. اتصال سوکت و همه تست‌ها بدون مشکل کار می‌کنند.
