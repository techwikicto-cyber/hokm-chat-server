# تستر مستقل چت سرور هکم

ابزاری برای بررسی سلامت چت سرور از هر جایی. **هیچ تغییری در سرور لازم ندارد** — نه
ری‌استارت، نه متغیر محیطی، نه یک خط کد.

دو حالت دارد:

- **CLI** — روی هر سروری، بدون مرورگر. عیب‌یابی شبکه + ۹ تست فانکشنال + تحلیل.
- **مرورگر** — دو کلاینت زنده کنار هم برای تست دستی و دیدن پیام‌های رد و بدل شده.

هر دو از یک فایل سناریو مشترک (`lib/scenarios.js`) استفاده می‌کنند، پس هیچ‌وقت از هم جدا نمی‌افتند.

## سریع‌ترین راه: Docker Compose

```bash
cd test-client
cp tester.env.example tester.env    # آدرس سرور و کلید AES را داخلش بگذارید

docker compose run --build --rm tester              # عیب‌یابی شبکه + همه تست‌ها
docker compose run --build --rm tester --diagnose   # فقط شبکه
docker compose run --build --rm tester --verbose    # با لاگ کامل هر پیام
docker compose run --build --rm tester --json       # خروجی ماشین‌خوان
docker compose up --build ui                        # حالت مرورگر روی :8080
```

هر آرگومانی که بعد از `tester` بنویسید مستقیم به `cli.js` می‌رسد.

`--build` را جدی بگیرید: کامپوز وقتی ایمیج از قبل وجود داشته باشد دوباره build
نمی‌کند، حتی اگر `Dockerfile` عوض شده باشد. اگر بعد از یک `git pull` رفتار قدیمی
دیدید، تقریباً همیشه علتش همین است.

اگر هشدار `The "C" variable is not set` دیدید، یعنی یک فایل `.env` در این پوشه
مانده — با `rm -f .env` پاکش کنید.

سرویس `tester` با `network_mode: host` اجرا می‌شود، پس اگر سرور چت روی همان ماشین
است `CHAT_URL=http://127.0.0.1:3008` کار می‌کند. روی Docker Desktop مک/ویندوز این
گزینه پشتیبانی نمی‌شود؛ آن خط را کامنت کنید و به‌جای `127.0.0.1` از
`host.docker.internal` استفاده کنید.

`tester.env` کلید AES را نگه می‌دارد، پس نه در گیت می‌رود و نه داخل ایمیج.

چرا اسمش `.env` نیست: کامپوز فایلی به اسم `.env` را خودکار می‌خواند و داخل مقدارهایش
دنبال متغیر می‌گردد. کلید AES این پروژه به `$C` ختم می‌شود و کامپوز آن را یک متغیر
خالی حساب می‌کرد، یعنی هم هشدار `The "C" variable is not set` می‌داد و هم کلید را
خراب می‌کرد. با این نام و `env_file`، مقدارها دست‌نخورده به کانتینر می‌رسند.

## بدون Compose

```bash
cd test-client
docker build -t hokm-chat-tester .

docker run --rm hokm-chat-tester \
  --url http://<ip>:<port> \
  --key 'کلید-۳۲-کاراکتری-AES'
```

ایمیج را یک بار بسازید و روی هر سروری در هر لوکیشنی اجرا کنید. برای فرستادن ایمیج به سرور دیگر:

```bash
docker save hokm-chat-tester | ssh root@other-server docker load
```

با متغیر محیطی هم می‌شود، که برای CI تمیزتر است:

```bash
docker run --rm \
  -e CHAT_URL=http://1.2.3.4:3008 \
  -e AES_KEY='p2s5v8y/B?E(H+MbPeShVmYq3t6w9z$C' \
  hokm-chat-tester
```

برای حالت مرورگر داخل داکر:

```bash
docker run --rm -p 8080:8080 --entrypoint node hokm-chat-tester server.js
```

## بدون Docker

```bash
cd test-client
npm install          # فقط دو کلاینت socket.io
node cli.js --url http://<ip>:<port> --key '...'
```

عیب‌یابی شبکه اصلاً پکیجی لازم ندارد و بدون `npm install` هم کار می‌کند:

```bash
node cli.js --url http://<ip>:<port> --diagnose
```

## گزینه‌ها

```
  -u, --url <آدرس>      آدرس سرور چت (یا متغیر CHAT_URL)            [الزامی]
  -k, --key <کلید>      کلید AES سرور، دقیقاً ۳۲ کاراکتر (یا AES_KEY)
  -r, --room <نام>      نام اتاق عمومی (یا PUBLIC_ROOM)   [پیش‌فرض public_chat_room]
  -t, --timeout <ms>    تایم‌اوت هر مرحله                  [پیش‌فرض 10000]
  -d, --diagnose        فقط عیب‌یابی شبکه، بدون نیاز به npm install
      --only <کلیدها>   فقط این سناریوها، با کاما جدا شده
  -v, --verbose         لاگ کامل هر پیام رد و بدل شده
      --json            خروجی JSON برای اسکریپت‌نویسی و مانیتورینگ
  -h, --help            راهنما
```

کد خروجی `0` یعنی همه‌چیز سالم، `1` یعنی چیزی خراب است — برای cron و مانیتورینگ آماده است.

## عیب‌یابی شبکه

لایه‌ها جدا تست می‌شوند تا وقتی چیزی کار نمی‌کند دقیقاً معلوم باشد **کجا** شکسته:

| لایه | چه چیزی را جدا می‌کند |
|---|---|
| **DNS** | نام دامنه resolve می‌شود؟ |
| **TCP** | پورت باز است؟ «refused» یعنی چیزی گوش نمی‌دهد، «timeout» یعنی فایروال بسته‌ها را drop می‌کند — دو مشکل کاملاً متفاوت |
| **Latency** | min/avg/max روی چند نمونه |
| **HTTP** | سرور جواب HTTP می‌دهد؟ health سرور چت است یا nginx وسط است؟ |
| **engine.io** | handshake سالم است؟ سرور socket.io v2 است یا v4؟ |
| **WebSocket** | ارتقا به websocket واقعاً انجام می‌شود؟ (nginx بد تنظیم‌شده اینجا لو می‌رود) |
| **CORS** | هدرهای CORS برای کلاینت‌های وبِ دامنه دیگر |

اگر لایه‌ای بشکند، همان‌جا متوقف می‌شود و می‌گوید چرا — چون تست لایه‌های بالاتر بی‌معنی است.

نسخه socket.io از روی شکل پاسخ handshake تشخیص داده می‌شود و کلاینت درست انتخاب
می‌شود؛ کلاینت v2 و v4 با هم حرف نمی‌زنند.

## تست‌های فانکشنال

| کلید | تست | چه چیزی را ثابت می‌کند |
|---|---|---|
| `connect` | اتصال + `get_user_details` | هندشیک، درستی کلید AES، بارگذاری تاریخچه |
| `public-broadcast` | چت عمومی A → B | پخش پیام و ساختار `sender_details` |
| `public-history` | تاریخچه عمومی | `INSERT`/`SELECT` جدول `public_chat` |
| `private-broadcast` | اتاق خصوصی | `join_chat_room` و پخش در اتاق |
| `private-history` | تاریخچه خصوصی | `INSERT`/`SELECT` جدول `private_chat` |
| `anti-flood` | کول‌داون ۸ ثانیه | ضدفلود روی Redis |
| `filters` | فیلتر متن | حذف شماره موبایل و کاراکترهای خاص |
| `unauthenticated` | ارسال بدون احراز هویت | سرور باید `request_user_details` بدهد |
| `malformed` | payload خراب | سرور نباید بیفتد |

اگر کلید AES اشتباه باشد، ابزار **بلافاصله** می‌گوید — به‌جای این‌که ۹ تست یکی‌یکی تایم‌اوت بخورند.

## تحلیل

ترکیب نتایج معنی می‌دهد، نه فقط تک‌تکشان. مثلاً اگر پیام در MySQL ذخیره شود ولی به
هیچ کلاینتی نرسد، ابزار می‌گوید مشکل فقط لایه پخش است و علت‌های محتمل را نام می‌برد:

```
تحلیل
─────────────────────────────────────
  پیام در MySQL ذخیره شد ولی به هیچ کلاینتی نرسید.
  یعنی سرور پیام را کامل پردازش کرد و فقط لایه پخش کار نمی‌کند. سه علت محتمل:
    • ناسازگاری نسخه: socket.io v4 با پکیج socket.io-redis کار نمی‌کند...
    • حالت cluster بدون SHOULD_USE_NGINX_REDIS=true...
    • نام اتاق عمومی با PUBLIC_ROOM_NAME سرور فرق دارد.
```

## حالت مرورگر

```bash
node server.js          # پیش‌فرض روی 8080
PORT=9000 node server.js
```

بعد `http://localhost:8080` را باز کنید، آدرس سرور و کلید AES را بدهید و **اتصال** را بزنید.
مقادیر در مرورگر ذخیره می‌شوند.

اگر تستر روی سرور ریموت است و نمی‌خواهید پورت را در فایروال باز کنید:

```bash
ssh -L 8080:localhost:8080 root@<server>
```

رمزنگاری AES در پروسه Node انجام می‌شود نه در مرورگر، چون Web Crypto فقط روی HTTPS یا
localhost کار می‌کند — این‌طوری با `http://<ip>:8080` هم کار می‌کند.

## نکاتی که موقع تست به کارتان می‌آید

- سرور با `socket.to(room)` پخش می‌کند، پس **فرستنده پیام خودش را دریافت نمی‌کند**.
  برای همین همیشه دو کلاینت لازم است.
- کول‌داون ضدفلود بر اساس `user_id` است. تست‌ها قبل از هر ارسال یک `user_id` تصادفی
  می‌سازند تا گیر نکنند؛ در تست دستی اگر پیام دوم رد شد، ۸ ثانیه صبر کنید.
- نام اتاق خصوصی اگر عددی و کوچک‌تر از `10000000` باشد، سرور عمداً ذخیره‌اش نمی‌کند
  (پخش زنده انجام می‌شود ولی تاریخچه نه).
- اگر سرور با `IS_LOCAL=true` بالا آمده باشد CORS خاموش است. فقط نمایش health در حالت
  مرورگر تحت تأثیر است؛ تست‌ها کار می‌کنند.
- **چت سرور با قطع شدن Redis کرش می‌کند** (کلاینت redis رویداد `error` بدون شنونده
  می‌فرستد). پس «Redis خوابید» معمولاً به شکل «سرور اصلاً جواب نمی‌دهد» ظاهر می‌شود،
  که ابزار در لایه TCP تشخیصش می‌دهد.
